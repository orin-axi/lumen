### Codex parse loop — far more sophisticated than a line-by-line map

`createParser` (line 644) is a **stateful streaming state machine**, not a simple map: it tracks `pendingTools`/`pendingToolSequence` per in-flight task, pairs `function_call`/`custom_tool_call` → `function_call_output`/`custom_tool_call_output` via a `call_id`→startTime `Map` (`openToolStarts`), and on `task_complete` computes **active-generation-time vs. tool-wait-time**, apportioning the task's total duration across pending calls by each call's share of generated tokens — a timing model well beyond Lumen's flat per-turn `latency_ms`.

Two findings with real correctness implications for Lumen:
1. **Session forking (`forked_from_id`)**: when a session is forked, Codex *replays* prior events with their original timestamps. CodeBurn explicitly detects this (`forkCutoff` = fork's own timestamp + 5s) and **skips re-counting replayed `task_started`/`task_complete`/tool events** to avoid double-billing. Lumen's model has no concept of this at all — a forked/resumed Codex session would likely double-count tokens today.
2. **Resumable/incremental parsing**: the whole loop is designed to re-enter from a byte offset (`tracker.lastCompleteLineOffset`) and cached prior results, for re-parsing only newly-appended lines on a growing session file. Lumen currently re-parses whole files every run — fine for one-shot `lumen audit`, but relevant if a daemon/watch mode is ever built.

Tool events observed in the real vocabulary: `function_call`/`function_call_output` **and** `custom_tool_call`/`custom_tool_call_output` — the one real session sampled earlier only showed the `custom_tool_call*` pair; `function_call*` is a second, apparently older/alternate vocabulary Codex still emits in some paths.

Confirms the SQLite `message.data`/`part.data` shapes match what was found querying the real DB directly. `buildAssistantCall` reads `data.tokens.{input,output,reasoning,cache.{read,write}}` **or** falls back to `data.usage.{input_tokens,output_tokens,cache_creation_input_tokens,cache_read_input_tokens}` — two possible shapes depending on OpenCode version/config, both handled. `normalizeToolName` maps raw tool names (`bash`→Bash, `edit`→Edit, etc.) and synthesizes `mcp__{server}__{tool}` for anything with an underscore not otherwise matched — a generic MCP-naming fallback Lumen's adapters don't have.

**Classification is per-turn, not per-session, and it's a two-stage hybrid (structural signal first, text signal second) — not a threshold ratio.**

`classifyTurn` first checks *which tools were actually called* (edit tools, read tools, bash, task tools, search/MCP, skill, plan-mode flag, agent-spawn flag) to assign a coarse category — `planning`, `delegation`, `testing`, `git`, `build/deploy`, `coding`, `exploration`, `general`. Only if the turn used *zero* tools does it fall back to pure text classification (`classifyConversation`, regex-matching the user message for brainstorm/research/feature/debug keywords → `brainstorming`/`exploration`/`feature`/`debugging`/`coding`/`conversation`). When a tool-based category is `coding` or `exploration`, a second pass (`refineByKeywords`) specializes it further via keyword regex into `refactoring`/`feature`/`debugging` (coding) or `exploration`/`debugging` (exploration) — using a documented **first-match-wins-by-position** tie-break rule, added specifically because "add error handling" was misclassified as `debugging` (the DEBUG regex fired before FEATURE) until they fixed it to pick whichever keyword appears *earlier in the sentence* (issue #196).

This is a materially different design from Lumen's spec: Lumen's `BimodalMode` is a *session-level*, two-bucket (Acceleration/Exploration/Balanced) classification from two numeric ratios (`mutation_density`, `search_turn_count`). CodeBurn's is *turn-level*, ~11 categories, tool-usage-primary with text-secondary refinement. CodeBurn's finer granularity and validated tie-break logic suggests Lumen's ratio-threshold approach is real but coarser — it would collapse CodeBurn's `git`/`testing`/`build-deploy`/`planning`/`delegation` distinctions into one bucket. Not necessarily wrong for Lumen's stated purpose, but worth knowing it's a simplification, not the industry-standard approach.

**A retry-counting heuristic with a documented false-positive fix.** `countRetries` walks each turn's tool-call sequence, tracking edit→verify→re-edit per *file*: an edit followed by a "verify-shaped" bash command (test/build, *not* a read-shaped one like `rg`/`cat`/`git log`) followed by another edit to the same file counts as one retry. The read-vs-verify distinction was added after issue #941 — treating any bash call between edits as a "verify" penalized bash-first workflows where `grep` between edits is research, not verification. Lumen has nothing like this signal at all.

**`workflow-insights.ts` covers three metric families Lumen doesn't have any equivalent of:**
- **User-correction detection** (`scanUserCorrections`): regex-matches the *user's* follow-up messages for correction language ("that's not what I meant", "you missed/forgot/misunderstood", "revert that/it/this"). Deliberately conservative — bare "wrong"/"undo" excluded because they appear in ordinary requests too; comments cite specific false-positive tuning against real data ("a well-composed page is never the wrong answer" produced 4 phantom corrections).
- **Time-to-first-edit** (`medianTimeToFirstEditMs`): per-session latency from session start to the first edit-tool call, median across sessions — a directness/efficiency signal.
- **File churn ranking** (`aggregateFileChurn`): ranks files by distinct-session rework count then edit-call count, with path normalization (backslash→forward-slash, home-dir relativization) explicitly to avoid leaking absolute paths/usernames in exported data — a privacy-conscious detail worth noting if Lumen ever exports similar rankings.

## Trajectory evaluation — Lumen's approach is directionally validated, with a more rigorous methodology now published

- **RedundancyBench** ([arXiv:2605.29893](https://arxiv.org/abs/2605.29893)) formalizes exactly what Lumen's Tarjan-SCC cycle detection is trying to catch — a benchmark of agent trajectories with each step labeled by whether it contributed to task completion, distinguishing genuinely redundant steps from necessary-looking-redundant ones. Lumen's fixed cycle-depth-≥3 threshold is a much coarser proxy for the same underlying question; RedundancyBench's per-step contribution labeling is the more rigorous target to validate against, not just "no repeated reads."
- **Graphectory** (referenced in the trajectory-evaluation search results) encodes execution traces as graphs and computes process-centric metrics *independent of task success* — structurally the same idea as Lumen's `TrajectoryGraph`/monotonicity approach. This is a real, named methodology in the same design space, worth reading directly for its exact metric definitions.
- The field has broadly moved to **process-level, not just outcome-level, evaluation**: SWE-Bench Pro, SWE Atlas, and AgentLens (the "Lucky Pass Problem" — an agent can pass a task via a wrong-reasoning path) all argue binary pass/fail is insufficient. This validates Prism's `RedGreenGrader` (pass/fail) + `TrajectoryGrader` (efficiency) combination directionally, but neither has been benchmarked against these newer suites' actual methodology.

## LLM-as-judge — real, well-documented reliability problems Prism's unbuilt `CalibratedJudge` needs to account for, not ad hoc

Multiple 2026 papers converge on the same finding: naive LLM-as-judge is measurably unreliable without explicit correction.
- A large systematic evaluation (21 judges, 9 providers, ~541K judgments, [arXiv:2606.19544](https://arxiv.org/abs/2606.19544)) found judge rankings shift by **up to 14 positions** across benchmarks, and — critically — **high test-retest reliability (&gt;0.95) can coexist with severe position bias (&gt;0.10)** in production-deployed judges, meaning a judge can look stable while still being systematically biased by anchor/example ordering. Exact-match agreement (a common validation metric) "systematically overstates discriminative ability" — kappa-corrected agreement drops 33–41 percentage points from raw agreement.
- **CalibraEval** ([arXiv:2410.15393](https://arxiv.org/pdf/2410.15393)) is a specific, citable calibration technique for mitigating selection bias in LLM judges.
- Named bias categories to design against explicitly: selection, position, contextual, self-reinforcing bias ([arXiv:2604.23178](https://arxiv.org/pdf/2604.23178) surveys mitigation strategies for each).

**Implication for Prism**: `CalibratedJudge`'s planned "contrastive few-shot anchors" design is on the right track (anchors are a real mitigation pattern) but needs explicit position-bias controls (anchor order randomization/reporting) and a calibration step — not just anchors alone — or it will likely reproduce the exact position-bias-with-high-apparent-reliability failure mode documented above.

## The real spec (github.com/open-telemetry/semantic-conventions-genai, status: Development, v1.44-1.56 range)

**Per-call inference spans**, not a single session-level span: each LLM call gets its own `CLIENT`-kind span named `{gen_ai.operation.name} {gen_ai.request.model}` (e.g. `"chat gpt-4"`). Key attributes on that span:
- `gen_ai.conversation.id` — **conditionally required on every inference span**, the session/thread correlator. This is a **singular ID per conversation**, attached to many spans — not a list.
- `gen_ai.response.id` — per-call completion identifier (e.g. `chatcmpl-123`).
- `gen_ai.request.previous_response.id` — an explicit, standard attribute for **threading multi-turn conversations** by referencing the prior call's response id.
- `gen_ai.conversation.compacted` (boolean) — a **standard flag for context-compaction events**.
- Token usage: `gen_ai.usage.{input_tokens, output_tokens}`, `gen_ai.usage.cache_read.input_tokens`, `gen_ai.usage.cache_write.input_tokens` (not "cache_creation" — Lumen's own naming diverges slightly here), plus `reasoning.output_tokens` and modality-specific variants (audio/image).
- **Tool calls are a separate span type** ("Execute tool span"), not folded into the inference span. Tool-call identity uses `gen_ai.tool.call.id` — an application-level identifier, matching Lumen's *existing* `call_id` field, not a distinct concept.
- **Agent/multi-agent**: `gen_ai.agent.id`, `gen_ai.agent.name`, `gen_ai.agent.description`, `gen_ai.workflow.name` — standard, provider-neutral attributes for representing an agent and multi-agent workflow, entirely separate from any application's own plugin/skill vocabulary.
- A dedicated `mcp.md` file exists — MCP tool calls have their own semantic conventions, separate from generic tool calls.

## Verdict on Lumen's design

**`otel_request_ids: SmallVec&lt;[CompactString; 2]&gt;` on `CanonicalTranscript` is built backwards relative to the real spec.** The real correlator is `gen_ai.conversation.id` — one ID per session, attached to *many* per-call spans — not a small list of "request ids" collected at the transcript level. Lumen's field name and shape don't map cleanly onto either `gen_ai.conversation.id` (singular, session-scoped) or `gen_ai.response.id` (per-call, would need to live on `CanonicalTurn`, not the transcript). `OtelCorrelationAccumulator`'s "dedupe multiple IDs into a unique set" behavior only makes sense if it was implicitly modeling "one `gen_ai.response.id` per turn" — but that's not how it's named or where the field lives.

**`otel_span_id: Option&lt;CompactString&gt;` on `CanonicalToolResult` conflates two distinct real concepts.** A real OTel *trace span_id* is a protocol-level 16-hex-char identifier from distributed tracing — a materially bigger feature (proper trace_id/span_id/parent-span linkage) than what `SpanMappingAccumulator` currently does (a flat `call_id → span_id string` map). What Lumen's `SpanMappingAccumulator` is actually trying to represent — correlating a tool invocation to *something* — already has a real, simpler answer: `gen_ai.tool.call.id`, which is functionally identical to the `call_id` field Lumen's `CanonicalToolCall`/`CanonicalToolResult` already have. If the goal is real distributed-tracing span correlation (linking into a Jaeger/Tempo backend), that's a legitimately bigger, currently-unscoped feature; if the goal was just "which tool call is this," Lumen may not need a new field at all.

**Not represented in Lumen's canonical model at all, but standard:** `gen_ai.agent.name`/`gen_ai.workflow.name` for multi-agent representation — a cleaner, ecosystem-agnostic alternative to the `AttributionSource::{Plugin,Skill}` taxonomy problem found earlier this session (Antigravity's real plugin/skill concept doesn't map onto Lumen's enum; the OTel convention's agent/workflow attributes are generic enough that any orchestrator's adapter could plausibly populate them). Also unrepresented: `gen_ai.conversation.compacted` (Lumen has its own PreCompact snapshot-merge logic already — this is a real, standard way to flag the same concept for OTel export) and `gen_ai.request.previous_response.id` (a standard turn-threading mechanism Lumen's own turn-ordering doesn't need since it has `turn_index`, but relevant if Lumen ever *exports* OTel data rather than just correlating with externally-produced traces).

**Bottom line**: neither `otel_request_ids` nor `otel_span_id` should be built as currently named/shaped without a redesign. The real spec gives exact target attribute names and a clear span/attribute structure to build against instead of inventing field names that sound OTel-adjacent.

## Findings

**1. **Scope correction found immediately**: `OpenHands/OpenHands` (the repo the directive named) is now *only* the React/TypeScript frontend — confirmed via its own `AGENTS.md`, which documents a 5-repo split. The actual agent loop lives in `OpenHands/software-agent-sdk` (Python). All findings below are from that repo. Also noticed but out of scope: sibling repos `OpenHands/agent-analysis`, `OpenHands/trajectory-visualizer`, `OpenHands/rubric`, `OpenHands/critic-rubrics`, `OpenHands/ToM-SWE` — names suggest direct relevance to both Lumen (trajectory analysis) and Prism (grading/rubrics), worth a dedicated look later.

**1. Event/Action/Observation hierarchy** (`openhands-sdk/openhands/sdk/event/base.py`): all events derive from one `Event` base with `id`, `timestamp`, `source`, and critically a `parent_id` — events form an explicit **tree**, not a flat list ("events sharing a parent_id are sibling branches"). This is structurally richer than a linear `CanonicalTranscript`. `LLMConvertibleEvent` subtypes reconstruct multi-tool-call LLM turns by grouping `ActionEvent`s sharing one `llm_response_id`.

**2. Sub-agent delegation** (`openhands-tools/.../delegate/impl.py`): agents are spawned with user-chosen string IDs, not auto-generated, capped by `max_children` (default 5). Delegated tasks run in parallel via real threads, blocking until done. Sub-agent metrics are **replaced, not merged**, per `agent_id` on each delegation — an explicit anti-double-counting measure. Nesting is structural (any sub-agent can itself delegate) via the same `parent_id` tree, not a hardcoded one-level pair — directly contradicts Lumen's `CircuitBreakerAccumulator` model of a single `parent-&gt;{agent_type}` string key, which cannot represent multi-level or multiple-distinct-child spawns at all.

**3. Loop/stuck detection** (`openhands-sdk/.../conversation/stuck_detector.py`): NOT graph-cycle-based — five independent pattern checks over a *windowed* (last 20 events, since last user message) scan: (a) identical action+observation repeated N times, (b) same action erroring N+1 times in a row (with a one-shot corrective "nudge" injected into the conversation, deduped so it doesn't refire on a frozen streak), (c) agent monologue — N consecutive agent messages with no user interruption, (d) alternating period-2 A-B-A-B pattern specifically (does not generalize to longer cycles), (e) context-window-error loop — explicitly `# TODO: blocked by` a tracked issue, i.e. a known, documented, unsolved gap even in this project. Equality checks explicitly ignore IDs/metrics, comparing only semantic content. Net: Lumen's Tarjan-SCC is more general (catches arbitrary-length cycles) than OpenHands' fixed-period pattern-matching — a second independent point in Lumen's favor — but OpenHands covers monologue and error-streak-with-live-intervention, two categories Lumen has nothing for.

**4. Persistence** (`conversation/event_store.py`): one file per event under an `EVENTS_DIR`, indexed by both position and UUID, protected by a `.eventlog.lock` file — documented as unreliable on NFS/network filesystems. No live/persisted divergence: the store IS the reconstituted state (rebuilt by scan on load), not a separate export format.

**5. Compaction** (`event/condenser.py`): a first-class `Condensation` event carries `forgotten_event_ids` (exact set removed) and an optional `summary`/`summary_offset` for where to splice a summary back in — more precise than a boolean flag; models exactly what was removed, not just that compaction happened.
